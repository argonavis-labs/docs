A metric drops on Tuesday. The team notices Friday.

By then you've spent three days sending more users into the same problem. Opening Mixpanel or GitHub wasn't the expensive part. Nobody was checking the metric against open issues and recent releases.

That's a good job for a Runner.

<Note>
  Writes follow your [tool permissions](/connections/tool-permissions). Keep issue creation, status changes, and team posts on **Ask** while you test. Runner stages each write as an **Action Card**. **Allow** acts without asking. **Off** blocks the tool unless the Runner has its own override.
</Note>

## Start with customer and delivery impact

| Runner | What it checks | Useful result |
|--------|----------------|---------------|
| **Customer-impact check** | Approved product metrics, open issues, and recent releases | Meaningful changes with evidence and one next investigation |
| **Delivery risk** | Linear projects, due dates, blockers, and pull requests | Work likely to slip because the owner, dependency, or next step is missing |
| **Bug intake** | Support or feedback source and existing issues | New reports grouped with duplicates and a draft issue for review |
| **Release summary** | Merged pull requests, completed issues, and release notes | A summary tied to the work that actually merged |
| **Weekly product review** | Shipped work and approved usage metrics | What moved, what didn't, and where the data is still inconclusive |

Runner can connect the evidence. It can't prove that one deploy caused a metric change just because the timestamps are close.

## Build this first: customer-impact check

```text
Create a Runner named Customer Impact Check.

Every weekday at 8:30am in my timezone, review the approved product metrics in
Mixpanel, high-priority open issues in Linear, and recent releases in GitHub.

Use the thresholds in this Runner's Project. Only include:
- a key metric outside its approved range
- a funnel step that changed more than the approved threshold
- a new high-priority issue with no owner or next step
- a release with a related open issue or documented customer report

For each item, cite the metric period, event or funnel, Linear issue, and GitHub
release used. Separate facts from possible explanations. A nearby release is a
lead to investigate, not proof of cause.

Recommend one next check. Don't roll back code, change issue status, assign an
owner, or post to Slack. Draft a Linear issue or team update only when the
sources contain enough detail for a person to review it.

If nothing matches, say that clearly and stop. Before you create the Runner,
show me the final name, prompt, schedule, and timezone. Wait for my confirmation.
```

**A user-created Runner becomes active as soon as it's created.** Open it, assign the Project that contains your approved thresholds, review its schedule and permissions, then click **Run now**.

Use a schedule that matches how quickly your team can respond. A daily check nobody reads is worse than a twice-weekly check somebody owns.

## Keep the rules out of one run

Put the rules in a product Project:

- The handful of metrics that actually matter.
- Approved thresholds, comparison windows, and timezone.
- Severity definitions and team ownership.
- Release and issue naming conventions.
- Actions Runner may draft but must not take.

Metrics, issues, and releases are the live state. Project context holds the rules. Previous run output doesn't carry forward automatically.

Review the first few results with write tools on **Ask**. Tighten a noisy threshold. Remove a vanity metric. Add the missing owner. That work belongs in the saved prompt or Project, not in feedback left inside one run.

## What comes next

### Delivery risk

Run each weekday morning. Find projects due in the next 14 days with blocked work, missing owners, overdue dependencies, or no recent update. Name the evidence and draft the question for the owner.

### Bug intake

Run each weekday morning. Group new reports by the product area and symptoms shown in the source. Search existing Linear issues before drafting a new one. A person still chooses severity and priority.

### Release summary

Run Friday after your normal release window. If no release appears in the source since the previous check, stop. Otherwise, pull merged work and completed issues into a customer-facing and internal draft. Don't claim impact before the data exists.

### Weekly product review

Run Friday afternoon. Compare shipped work with the approved metrics and open customer reports. Call out missing or inconclusive data instead of forcing a win.

## Protect the work that already shipped

The goal isn't more tickets. It's catching a customer problem earlier, keeping an important project from slipping, and giving the team evidence before it makes a decision.

That saves engineering time and protects revenue without pretending the system knows more than the sources do.
